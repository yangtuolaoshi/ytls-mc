# 一、测试目标

框架的测试，不是为了验证某个 Mod 玩法本身，而是为了验证框架是否能作为“通用开发底座”使用。

测试目标应明确为：

1. **覆盖性**
   框架是否覆盖了原版和 Forge 的主要扩展点。
2. **抽象有效性**
   除少量高度复杂的场景，业务层是否真的可以不直接碰底层 Forge API。
3. **稳定性**
   在复杂场景下是否仍然可用，不崩、不乱、不丢数据。
4. **可复用性**
   新 Mod 分支是否能靠框架快速起步，而不是重新造轮子。
5. **可维护性**
   修改框架时，是否会大面积破坏已有业务分支。

------

# 二、测试需求

测试要求包含以下能力域

------

## 1. 注册体系测试

测试框架能否统一覆盖原版和 Forge 常见注册对象。

至少要测：

- 方块
- 物品
- 方块实体
- 实体类型
- 菜单类型
- 配方序列化器
- 音效
- 粒子
- 属性
- 附魔
- 状态效果
- 创造模式物品栏
- 世界生成相关注册
- 战利品表扩展
- 自定义数据类型

测试要求不是“能注册一个”，而是要测：

- 是否支持批量注册
- 是否支持自动补全资源关联
- 是否支持注册顺序正确
- 是否支持客户端/服务端分离
- 是否支持重复注册、缺失注册的报错提示

------

## 2. 生命周期测试

测试框架是否准确映射 Minecraft 和 Forge 的生命周期。

至少要覆盖：

- Mod 构造阶段
- Common Setup
- Client Setup
- Data Generation
- Server Starting
- Server Started
- World Load / Unload
- Player Join / Leave
- Resource Reload
- Config Reload
- Shutdown

测试要求：

- 生命周期顺序是否正确
- 某阶段失败后是否能给出明确错误
- 客户端专属代码是否不会在服务端误执行
- 数据生成是否不污染运行环境

------

## 3. 事件系统测试

测试框架是否真的把原始 Forge 事件整理成了业务可用的语义事件。

至少要覆盖：

- 玩家登录/退出
- 玩家伤害/死亡/复活
- 实体生成/死亡/受击
- 方块放置/破坏/右键
- 物品使用/丢弃/拾取
- 世界时间变化
- 区块加载
- 维度切换
- GUI 打开/关闭
- 资源重载

测试要求：

- 事件是否能拿到完整上下文
- 事件是否支持取消、拦截、修改结果
- 事件优先级是否正确
- 连续事件链是否不会乱序
- 框架封装后，业务层是否不需要直接写 Forge 监听器

------

## 4. 网络与同步测试

这是最容易出问题的地方，必须重点测。

至少覆盖：

- 客户端发包给服务端
- 服务端发包给客户端
- 单人模式与联机模式
- 实体状态同步
- 玩家状态同步
- 方块实体同步
- 自定义组件同步
- 容器同步
- 配置同步
- 广播与定向发送

测试要求：

- 数据一致性
- 延迟下是否正确
- 断线重连后是否恢复正确
- 错误包是否能被拒绝
- 客户端篡改数据是否会被服务端纠正
- 大量同步时是否会卡顿或丢包

------

## 5. 数据挂载与能力测试

至少要覆盖：

- 玩家附加数据
- 实体附加数据
- 方块实体附加数据
- 世界附加状态
- 临时数据与持久数据
- 复制、死亡、换维度、重载后的状态恢复

测试要求：

- 序列化是否完整
- 复制时是否正确
- 同步时是否正确
- 持久化后重启是否正确
- 框架层是否屏蔽了底层实现差异

------

## 6. AI 与战斗测试

至少要覆盖：

- 普通生物 AI
- 敌对生物追击
- Boss 阶段切换
- 群体协作
- 环境感知
- 技能释放
- 多目标选择
- 状态变化驱动行为

测试要求：

- 行为决策是否稳定
- 状态切换是否不死循环
- 高压场景下是否还能运行
- 复杂 AI 是否可配置而不是写死
- 调试工具能否看见 AI 状态

------

## 7. 世界生成与规则测试

至少覆盖：

- 结构生成
- 生物群系相关效果
- 特征生成
- 矿脉生成
- 维度规则
- 特殊天气
- 全局灾变规则
- 区域规则

测试要求：

- 生成结果可预测
- 不同种子下运行正常
- 多维度切换不异常
- 配置改动后能正确生效
- 规则叠加时结果明确

------

## 8. 客户端表现测试

至少覆盖：

- 实体渲染
- 方块实体渲染
- 粒子
- 音效
- HUD
- 菜单界面
- 镜头效果
- 受击反馈
- 动画控制

测试要求：

- 客户端特性不会跑到服务端
- 表现与逻辑是否解耦
- 资源缺失时是否有降级方案
- 大量特效是否有性能问题

------

## 9. 数据生成与资源测试

至少覆盖：

- blockstate
- model
- loot table
- recipe
- lang
- tag
- 配置文件
- 结构数据

测试要求：

- 自动生成是否完整
- 生成内容是否能直接运行
- 覆盖手工资源时是否正确
- 资源改名后是否能正确追踪
- 缺失资源是否能提示清楚

------

## 10. 兼容与边界测试

至少覆盖：

- 单人
- 联机
- 专服
- 资源包叠加
- 数据包叠加
- 多模组共存
- 版本升级
- 模块热替换或分支迁移
- 异常输入
- 空数据
- 重复注册
- 资源缺失
- 事件冲突

测试要求：

- 不只是“正常能用”，还要“坏情况下能解释”
- 错误不能静默失败
- 与别的模组冲突时要能定位问题

------

# 三、测试标准

不要只用“通过/不通过”，而是用 **分级标准**。

------

## 1. 功能覆盖标准

每个能力域都要定义三个级别：

### L1：基础可用

- 能实现
- 能运行
- 能看到效果

### L2：框架化可用

- 业务层不需要直接接触底层 Forge 细节
- 能通过统一接口完成
- 不依赖手写模板代码

### L3：生产可用

- 能处理异常
- 能处理组合场景
- 能在多人、重载、冲突条件下稳定运行

框架至少要在核心能力上达到 L2，重点能力上达到 L3。

------

## 2. 覆盖率标准

每个条目都标注：

- 是否覆盖原版机制
- 是否覆盖 Forge 扩展
- 是否业务层可直接使用
- 是否支持同步（部分功能需要）
- 是否支持持久化（部分功能需要）
- 是否支持热重载（部分功能需要）
- 是否支持调试（部分功能需要）

------

## 3. 错误质量标准

很多框架不是不能用，而是出了问题完全不知道哪里错了，所以要把“错误质量”纳入测试标准。

标准包括：

- 报错是否明确指出对象名、阶段、模块、文件位置
- 是否能区分配置错误、资源错误、逻辑错误、同步错误
- 是否能在日志里快速定位
- 是否会静默失败

------
