# Minecraft Forge 开发框架需求文档

## 1. 项目定位

本项目不是一个普通的单体 Mod，而是一个用于 **快速创建、复制、裁剪、合并创意 Mod 分支的 Forge 开发框架**。
主分支的职责是给后续各类创意 Mod 提供统一的底座能力，目标类似于 “SpringMVC 对 Servlet 的封装”：让业务开发尽量不直接接触 Forge 的底层复杂度，而是通过框架暴露的统一接口、约定和模板快速落地玩法。

项目主要服务于以下场景：

- 通过 Git 从主分支拉出一个新分支，快速制作一个独立创意 Mod
- 一个分支通常只承担一个主题或一个玩法，不追求长期演进
- 分支之间如果需要联动，可通过合并代码或抽取公共能力的方式实现
- 开发重点是“快、少模板、低心智负担、易改造、易重构”
- 目标版本为 Minecraft Forge **1.20.X**，但考虑到每个游戏版本和Forge版本SDK的变化可能会很大，应当设计一套通用的接口，每次更换版本只需要修改或者重新写一套接口实现，从而保证上层的代码不需要改动
- 技术栈使用 **Java**，不使用 Kotlin

------

## 2. 总体目标

### 2.1 核心目标

1. **降低 Forge 开发复杂度**
   将注册、事件、网络、同步、能力、渲染、数据生成、资源管理等复杂内容封装为统一框架能力。
2. **减少模板代码**
   通过注解、约定优于配置、自动扫描、代码生成、统一基类等方式，尽量避免手写大量样板代码。
3. **兼容原版与 Forge 的大部分特性**
   框架不是替代 Minecraft 原生机制，而是在原版与 Forge 的生命周期、注册体系、事件体系之上做高层抽象。
4. **支持主分支 + 多创意分支的工作方式**
   主分支维护通用框架能力，各创意分支只关注玩法内容；需要联动时通过 Git 合并或提取公共模块处理。
5. **适配短周期创意开发**
   分支可能只存在于一个创意阶段，不强调长期稳定演进，但要求结构清晰、可复制、可快速推翻重做。

------

## 3. 设计原则

### 3.1 框架与业务分离

- 主分支只提供框架能力，不直接承载具体玩法
- 创意分支只编写玩法逻辑，不直接处理 Forge 底层机制
- 业务代码不应直接依赖 `DeferredRegister`、`FriendlyByteBuf`、`EventBus` 等底层细节

### 3.2 约定优于配置

- 默认通过注解、命名约定、目录约定、自动扫描完成大部分接入
- 尽量减少必须显式注册、显式绑定、显式同步的场景

### 3.3 统一抽象

- 同类能力必须统一入口，例如：
  - 统一注册入口
  - 统一事件入口
  - 统一网络入口
  - 统一同步入口
  - 统一数据入口
  - 统一调试入口

### 3.4 原版优先、Forge 兼容

- 优先复用 Minecraft 原版的系统与语义
- 在原版机制之上进行增强，而不是另起炉灶
- 必须兼容 Forge 生命周期与常见扩展能力

### 3.5 面向创意生产

- 框架目标不是极致通用，而是高频创意生产
- 优先优化：
  - 新玩法上线速度
  - 改动成本
  - 调试效率
  - 资源生成效率
  - 分支复制成本

------

## 4. 版本与技术约束

### 4.1 目标版本

- Minecraft：**1.20.X**
- Forge：对应 1.20.X 的稳定版本
- **【非常重要】考虑到每个游戏版本和Forge版本SDK的变化可能会很大，应当设计一套通用的接口，每次更换版本只需要修改或者重新写一套接口实现，从而保证上层的代码不需要改动**

### 4.2 技术语言

- 仅使用 **Java**
- 不使用 Kotlin
- 可以使用注解处理、反射、代码生成、字节码增强、Mixin 等 Java 生态常见技术

### 4.3 建议依赖方向

- Forge
- Mixin
- 数据生成工具链
- 可选脚本引擎：Lua 或类似轻量脚本方案
- 可选动画库：如 GeckoLib 风格的动画体系，但应统一封装，避免业务层直接耦合具体实现

------

## 5. 项目结构目标

框架应形成明确的三层结构：

### 5.1 基础层（framework）

负责与 Forge 和 Minecraft 原生机制交互，包含：

- 启动与初始化
- 注册体系
- 事件体系
- 网络体系
- 同步体系
- 数据体系
- 资源生成体系
- 调试体系
- 兼容适配层

### 5.2 业务层（gameplay）

负责创意 Mod 的具体玩法内容，包含：

- 方块
- 物品
- 实体
- 生物 AI
- 技能
- 世界规则
- 配方
- 战斗机制
- 事件规则
- 客户端表现

### 5.3 支撑层（generated / assets / configs）

负责自动生成或管理的内容，包含：

- blockstate
- model
- lang
- loot table
- recipe
- tag
- 配置文件
- 脚本文件
- 调试配置

------

## 6. 框架能力范围

框架需要覆盖 Minecraft 原版和 Forge 的大部分常见扩展点。

### 6.1 注册系统

目标：把所有注册逻辑统一封装，避免业务代码直接操作 Forge 注册细节。

需要支持：

- Block 注册
- Item 注册
- BlockEntity 注册
- EntityType 注册
- MenuType 注册
- RecipeSerializer 注册
- DamageType / DamageSource 相关扩展
- Potion / MobEffect 注册
- SoundEvent 注册
- ParticleType 注册
- Creative Tab / ItemGroup 相关注册
- Attribute 注册
- DataComponent / 自定义数据挂载
- Villager Profession / Poi / Sensor 等相关扩展
- Structure / Feature / PlacementModifier / Carver 等世界生成注册
- LootCondition / LootItemFunction / LootTable 扩展
- Codec / MapCodec 相关数据注册
- 其他 Forge 常见注册项

设计要求：

- 支持注解驱动注册
- 支持自动扫描包路径注册
- 支持统一命名规则
- 支持注册后自动补全客户端资源关联
- 支持默认模板与自定义工厂并存

------

### 6.2 生命周期管理

目标：统一处理 Forge 和原版加载流程，屏蔽复杂生命周期差异。

需要支持：

- mod 构造阶段
- common setup
- client setup
- datagen
- server starting
- server started
- world load / unload
- player login / logout
- resource reload
- config reload
- shutdown / cleanup

设计要求：

- 生命周期事件必须被框架统一封装
- 业务层使用语义化生命周期接口，而不是直接写 Forge 事件监听
- 支持按模块或按功能注册生命周期回调

------

### 6.3 事件系统

目标：将 Forge 零碎事件统一为业务可读的语义事件。

需要支持或未来能够扩展：

- 玩家事件
- 实体事件
- 方块事件
- 物品事件
- 世界事件
- 维度事件
- 战斗事件
- 交互事件
- 同步事件
- 客户端渲染事件
- 输入事件
- 资源重载事件
- 服务端生命周期事件

设计要求：

- 框架内部监听 Forge 原始事件
- 对外暴露语义化事件对象
- 事件对象需包含完整上下文
- 允许事件拦截、取消、修改结果
- 支持事件优先级和链式处理
- 支持统一订阅注解或统一监听接口

------

### 6.4 网络与同步系统

目标：彻底减少手写 Packet、编解码和同步逻辑。

需要支持或未来能够扩展：

- 客户端到服务端消息
- 服务端到客户端消息
- 广播消息
- 单目标消息
- 区域消息
- 容器同步
- 玩家状态同步
- 实体状态同步
- 方块实体同步
- 自定义组件同步
- 配置热同步

设计要求：

- 业务层尽量不直接操作 `FriendlyByteBuf`
- 提供统一消息定义模型
- 提供自动注册、自动编解码、自动派发
- 支持字段级同步配置
- 支持服务端权威数据同步
- 支持自动化安全校验，避免非法客户端写入

------

### 6.5 数据挂载与能力扩展

目标：为玩家、实体、方块实体、世界等对象提供统一附加数据能力。

需要支持或未来能够扩展：

- 玩家数据扩展
- 实体数据扩展
- 方块实体数据扩展
- 世界 / 维度级状态扩展
- 物品附加状态
- 临时运行态与持久化状态区分

设计要求：

- 业务层统一通过组件/数据接口访问
- 框架内部可使用 Capability 或原生等价机制实现
- 对业务层屏蔽底层附加实现方式
- 支持序列化、同步、持久化、复制、清理等生命周期

------

### 6.6 AI 与行为系统

目标：让复杂生物 AI 和 Boss 行为开发更直观。

需要支持或未来能够扩展：

- 目标选择
- 攻击行为
- 巡逻行为
- 逃跑行为
- 搜索行为
- 追击行为
- 技能释放
- 阶段切换
- 仇恨管理
- 群体 AI
- 环境感知
- 条件触发行为

设计要求：

- 对原版 Goal 系统做高层封装
- 可组合、可复用、可配置
- 支持状态机或行为树式抽象
- 支持按配置定义参数，减少手写逻辑
- 支持 Boss 多阶段和复杂战斗流程

------

### 6.7 技能与战斗系统

目标：支持创意 Mod 常见的技能、连招、特殊攻击和电影化战斗表现。

需要支持或未来能够扩展：

- 主动技能
- 被动技能
- 冷却时间
- 消耗系统
- 施法阶段
- 命中判定
- 伤害修正
- 连锁效果
- 范围效果
- 粒子特效联动
- 音效联动
- 动画联动
- 事件触发技能

设计要求：

- 技能逻辑统一建模
- 技能可配置化
- 技能状态可同步
- 支持客户端表现与服务端判定分离
- 支持脚本或数据驱动定义部分技能行为

------

### 6.8 世界规则与游戏规则系统

目标：支持创意玩法对世界状态的整体控制。

需要支持或未来能够扩展：

- 天气与昼夜规则
- 生成倍率
- 生物刷新规则
- 维度规则
- 时间流速规则
- 重力或环境规则
- 事件波次规则
- 血月、尸潮、灾变、污染扩散等世界级玩法

设计要求：

- 将世界级玩法封装为可启用规则
- 支持规则组合和优先级
- 支持全局、生物群系、维度、区域等不同作用域
- 支持动态启停和配置调整

------

### 6.9 资源与数据生成系统

目标：减少手写 JSON、模型、配方和语言文件。

需要支持或未来能够扩展自动生成：

- blockstate
- item model
- block model
- loot table
- recipe
- tag
- lang
- datagen 所需内容
- 结构数据与世界生成数据

设计要求：

- 以 Java 定义为主，自动输出资源文件
- 支持约定驱动的默认生成
- 支持显式覆盖默认资源
- 支持增量生成
- 支持根据注册信息自动补全大部分基础资源

------

### 6.10 客户端表现系统

目标：统一控制渲染、粒子、UI、动画和音效。

需要支持或未来能够扩展：

- 实体渲染
- BlockEntity 渲染
- HUD
- 菜单界面
- 技能提示
- 粒子效果
- 音效播放

设计要求：

- 客户端代码与服务端业务逻辑分离

------

### 6.11 配置系统

目标：让 Mod 行为可以快速调参和重构。

需要支持或未来能够扩展：

- 常规配置
- 服务端配置
- 客户端配置
- 世界配置
- 玩法配置
- 技能配置
- AI 配置
- 掉落配置
- 生成配置

设计要求：

- 支持统一配置定义方式
- 支持默认值、校验、注释、范围限制
- 支持运行时读取
- 支持热重载或尽量接近热重载的重新加载机制

------

### 6.12 脚本扩展系统

目标：为高频创意试错提供快速编排能力。

需要支持或未来能够扩展：

- 事件脚本
- 技能脚本
- 规则脚本
- 波次脚本
- 剧情脚本
- AI 行为脚本

设计要求：

- 脚本层只做编排，不承担底层系统实现
- 脚本必须可热加载或近似热加载
- 脚本与 Java 代码之间有明确边界
- 脚本调用框架能力时应使用安全受控 API

------

### 6.13 调试与开发辅助系统

目标：让开发、测试、录制视频的过程更快。

需要支持或未来能够扩展：

- 开发模式开关
- 调试命令
- 实体生成命令
- 技能测试命令
- AI 调试命令
- 状态查看命令
- 日志增强
- 配置重载命令
- 资源重载命令
- 运行时参数查看
- 性能统计
- 事件追踪

设计要求：

- 调试功能默认仅在开发环境或显式开启时可用
- 需要有统一日志前缀和模块标识
- 支持快速定位注册、同步、事件、渲染等问题

## 7. 分支工作模式设计

### 7.1 主分支职责

主分支负责维护“框架层”，主要内容包括：

- 框架核心代码
- 通用封装
- 自动化注册与数据生成
- 通用调试工具
- 通用兼容层
- 基础示例与模板

### 7.2 业务分支职责

业务分支只负责：

- 具体创意玩法
- 该玩法需要的资源与配置
- 该玩法的业务代码
- 该玩法的特定调试逻辑

### 7.3 联动方式

当两个创意 Mod 需要联动时，优先采用：

1. 提取公共能力回主分支
2. 通过 Git 合并引入联动逻辑
3. 使用清晰的兼容层或桥接层处理差异

不建议：

- 在业务分支里复制粘贴大量框架代码
- 直接绕开框架访问 Forge 底层 API

------

## 8. 编码风格与实现约束

### 8.1 Java 代码风格

- 使用清晰、稳定、低魔法的 Java 写法
- 控制泛型复杂度
- 控制反射滥用
- 控制过深继承
- 优先组合优于继承

### 8.2 注解与扫描

允许使用：

- 自定义注解
- 包扫描
- 类路径扫描
- 反射注入
- 注解处理器
- 代码生成

但要求：

- 行为必须可预测
- 错误提示必须明确
- 不允许“扫描不到就静默失败”

### 8.3 框架 API 设计

框架 API 应遵循：

- 简单入口
- 明确返回值
- 明确异常处理
- 默认行为合理
- 高级能力可扩展
- 业务层使用成本低

## 10. 优先级划分

### 10.1 第一优先级：必须先落地

- 启动与基础框架
- 注册体系封装
- 事件体系封装
- 网络与同步体系
- 配置体系
- 资源生成体系
- 基础调试体系

### 10.2 第二优先级：显著提升生产力

- 组件系统
- AI 框架
- 技能框架
- 世界规则系统

### 10.3 第三优先级：增强体验

- 脚本系统

## 11. 验收标准

框架达到可用状态的标准如下：

1. 新建一个创意分支后，能在较少样板代码的情况下完成一个基础 Mod
2. 方块、物品、实体、技能、配置、网络消息等内容能通过统一框架快速接入
3. 业务层代码不需要频繁接触 Forge 底层注册和事件机制
4. 常见资源文件能自动生成或半自动生成
5. 客户端与服务端逻辑分离清晰
6. 复杂玩法可通过框架封装完成，而不是每个分支重新写一套系统
7. 联动分支可以通过合并或共享框架能力快速实现
8. 业务分支删掉后不会影响主分支框架完整性

------

## 12. 最终交付目标

最终应交付一个基于 Minecraft Forge 1.20.X、使用 Java 编写的开发框架，使其具备以下特征：

- 作为主分支长期维护
- 作为所有创意 Mod 分支的统一底座
- 大幅减少 Forge 样板代码
- 覆盖原版与 Forge 的主要扩展能力
- 能支持快速做、快速改、快速废弃的短周期创意开发
- 能让后续新分支主要写“玩法”，而不是反复解决“框架问题”

------
